# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Inbox Classic is an email client for Windows, the Mac and Linux. On Windows it looks like Outlook Express; on the Mac (AppKit) and Linux (GTK 4 and libadwaita) it looks native to the system, with the same layout, features and words. It is a sibling of ImapKit Desktop (`../imapkit-win`), which has the same classic Win32 look but runs a Node.js sidecar. Inbox Classic has no sidecar: IMAP, SMTP and MIME run in-process in a Rust core, the same for all three apps.

The homepage, https://inboxclassic.com, is a static page in its own public repo `postalsys/inboxclassic.com` (`../inboxclassic.com`), served by GitHub Pages; its DNS is in Cloudflare. Its screenshots come from `build/ui-e2e`; refresh them when the windows change. The app repo is `postalsys/inbox-classic` (renamed from postal-express; the build machine's checkout path and this local folder keep the old name).

## Security model (the reason for the architecture)

Everything a remote party writes (IMAP responses, message headers and bodies, attachment names, autoconfig XML, DNS answers) is parsed only in Rust. The C++ code never parses remote data; it shows values the core has already decoded and validated, and passes sanitized HTML to WebView2 without changing it. Keep the C++ side minimal: new logic that touches mail data belongs in `core/`, not `app/`.

- **Rust (`core/`)**: IMAP, SMTP, MIME parsing and building, charsets, HTML sanitizing, the local store, `.eml` import and export, account autodiscovery, OAuth token exchange, credentials (Windows Credential Manager), and safe attachment filenames.
- **WebView2 (`app/src/preview.cpp`)**: renders the documents from `pe_html_render` with scripts, web messages, host objects and dev tools off. A `WebResourceRequested` filter on `*` refuses http(s), ftp and file requests (remote images only after the user allows them), and navigation and new windows are cancelled, with links opened in the default browser. Do not enable scripts to run a JS sanitizer such as DOMPurify; sanitizing is done in Rust (`pe-html`, ammonia) and the document carries a CSP as one more layer.
- **The editor (`app/src/editor.cpp`)**: the one WebView2 with a script, the compose window's HTML editor. The page comes from `pe_editor_document` (`pe-html/src/editor.rs`) and runs only its own `editor.js`, allowed by a random nonce in the CSP. The quoted message, sanitized in Rust without its style elements, waits in an inert `<template>`: "..." or Select All puts it into the editable text (then the page answers `full:` and the core does not add it again); folded, Rust adds it when sending. A saved draft opened again (`pe_draft_open`) starts the page with its body, sanitized again in `editor_document`; drafts are found and replaced by their Message-ID (`pe-sync` `save_draft`). `pe_html::outgoing_html` sanitizes everything sent again and turns `data:` pictures into `cid:` attachments. The page reports to C++ with plain strings (`html:`, `full:`, `state:`, `dirty`, the link at the cursor and under the mouse as `caret:` and `hover:`, `open:` for a Ctrl+clicked link, which C++ opens with `webview::OpenExternally` as the reading pane does), never JSON; `drop` carries the files dragged onto it as WebView2 File objects, whose paths C++ reads and hands to `pe_picture_uri` as Insert Picture does (other files are attached), so the page reads no file; network requests, navigation, dev tools, host objects and the browser keys are off. Keep editing logic in `editor.js` small and never let it handle message content beyond what the user edits.
- **C++ (`app/`)**: windows, common controls, menus, dialogs and plain app preferences.

## Rust core

A Cargo workspace in `core/` (edition 2024, `rustfmt.toml` sets 120 columns). The crates under `core/crates/`:

- `pe-imap`: port of `../imapflow/src`. `pe-smtp`: port of the client parts of `../nodemailer/src` (smtp-connection, mime-node, mail-composer, mime-funcs, qp, base64, xoauth2); message building matches nodemailer byte for byte, checked by `tests/conformance.rs` against fixtures from `tests/fixtures/generate-nodemailer-cases.mjs` (run with the path of a built nodemailer checkout). `pe-mime`: port of `../postal-mime/src`. Port these idiomatically rather than line by line: response parsing as pure functions over bytes, the connection on top of that. Use the TS test suites and fixtures of the originals as the reference for behavior.
- `pe-html`: ammonia sanitizer and the preview document wrapper with its CSP.
- `pe-net`: TCP and TLS (rustls with the platform verifier, or a pinned certificate) for IMAP and SMTP.
- `pe-store`: the local cache in SQLite (rusqlite, bundled): accounts without secrets, folders, message summaries, cached sources, and the search: a contentless FTS5 index (`messages_fts`: subject, senders, recipients, file names, text) and Gmail's query syntax (`query.rs`, turned into SQL with bound values and quoted FTS5 words in `search.rs`). The text comes from the core: a cached source parsed when a message is opened, or the text parts the workers fetch for every message in the background (`pe-sync` `fetch_texts`, BODY.PEEK of the parts BODYSTRUCTURE names, decoded in `pe-core/src/search.rs`). Conversations (`threads.rs`): each account's messages grouped by the Message-IDs they name (their own, In-Reply-To, References; on Gmail X-GM-THRID too), a list of one row per conversation with the expanded ones' messages under them, paged by offset; mail stored before is threaded and given its References by the worker in the background. Schema changes are new entries in `schema.rs` `MIGRATIONS`, never edits of shipped ones.
- `pe-sync`: keeps `pe-store` in step with an IMAP account through `pe-imap`.
- `pe-oauth`: OAuth 2.0 sign-in (authorization code with PKCE and a loopback redirect, RFC 8252) for Gmail and Outlook.com. Google's Desktop App client (project inbox-classic) is built in, its "secret" included, which for Desktop App clients is not one (RFC 8252 8.5; PKCE protects the flow); `PE_GOOGLE_CLIENT_ID` and `PE_GOOGLE_CLIENT_SECRET` at build time replace it. Microsoft's public client (Entra, any organization and personal accounts, no secret) is built in too; `PE_MICROSOFT_CLIENT_ID` replaces it. `tests/live.rs` (`PE_NETWORK_TESTS=1`) checks that Google and Microsoft accept the built-in clients and that the presets' issuers can be discovered. An account signed in this way always uses the provider's own servers. Sign-in apps (`pe-core/src/sign_in_apps.rs`, `pe-store` `sign_in_apps`): OAuth clients the user registered with any OpenID Connect provider, their endpoints from the issuer's discovery document (`pe-oauth/src/discovery.rs`, https only but for a loopback test issuer), their secret in the Credential Manager, accounts naming them `oauth2:app:<id>`; every sign-in app, the built-in clients included, can be turned off for new accounts (built-in Google is off out of the box, as Google lets only test users use it). ImapKit's OAuth provider (5.3 and newer, `oauth` in the harness configuration) is what the tests sign in against.
- `pe-autoconfig`: finds the servers of an address the way EmailEngine does (`../emailengine/lib/autodetect-imap-settings.js`, whose tests are the reference): first the domain's MX against a table of hosted providers, then a race of RFC 6186 SRV records, the provider's autoconfig file (and `/.well-known`), Thunderbird's ISPDB and Microsoft Autodiscover (POX and SOAP; the password only after a Basic challenge, over https, to that origin), then `imap.`/`smtp.` guesses. Also the app-password hints of providers that want one. DNS goes over DNS-over-HTTPS (Cloudflare, then Google), never plain DNS, so nobody on the network can hand out other servers. Never picks a server without encryption. `cargo run -p pe-autoconfig --example discover -- user@example.com [password]` tries it live.
- `pe-content`: port of `../email-content` (`analyze()`): separates what a sender wrote from the reply history and forwarded content their client attached. `tests/conformance.rs` compares it with email-content's own output on its test inputs and fixtures (`tests/fixtures/*.mjs` regenerate them from a built checkout). `pe-core/src/fold.rs` folds what it hides behind "..." in the reading pane.
- `pe-jsre`: JavaScript regular expressions on the `regex` crate for the ports of JavaScript libraries (pe-content, pe-bounce): ASCII `\d`, `\w` and `\b`, JavaScript's `\s` and `.`, `i` folding as JavaScript does without `u`, `m` ending lines at CR and LF, and leading lookaheads; its string helpers count UTF-16 code units.
- `pe-bounce`: bounces explained. `detect.rs` ports `../emailengine/lib/bounce-detect.js` (RFC 3464 reports, `X-Failed-Recipients`, the returned message, WorkMail and Zoho, text heuristics for prose notices, delay told from failure); its heuristics run only on mail from a mailer daemon or postmaster, with `Auto-Submitted`, or with a delivery report, so ordinary mail quoting an SMTP error is no bounce. `classify.rs` and `model.rs` port `../bounce-classifier/src` with its model in `model/` (`scripts/update-bounce-model.sh` replaces it and records its hashes). `analyze()` gives every failed or delayed recipient with the server's words and their category. `tests/conformance.rs` compares both with the originals (`tests/fixtures/generate.mjs` regenerates the fixtures from built checkouts).
- `pe-otp`: port of `../otp-detect` (`detectOtp()`, pinned to a tag): finds the one-time code in a message's text with its own HTML renderer, candidates, multilingual keywords and a gradient boosted model in `model/` (`scripts/update-otp-model.sh` replaces it and records its hashes). `tests/conformance.rs` compares every candidate's features and score with otp-detect's (`tests/fixtures/generate.mjs` regenerates them from a built checkout). `pe-core/src/otp.rs` offers a code (an `OTP-Token` header first, which pe-mime parses) only when the provider's Authentication-Results say the domain it is for signed the message; the card is `pe-html/src/otp.rs`, its Copy the link `inboxclassic:copy-code`.
- `pe-core`: the engine the C API wraps: a tokio runtime, the workers of each account (`worker.rs`, each with its own IMAP connection and store connection: the main one for syncs, IDLE and the user's commands, the reader for the messages opened (`worker/reader.rs`), the background one for conversations and search text (`worker/background.rs`); a server that refuses the extra connections gets their work done by the main one), the message view, and `Event`s for the windows. Passwords are kept in the Windows Credential Manager (`secrets.rs`); tests open the core with `PasswordStore::Memory` so they never write to the Credential Manager of whoever runs them.
- `pe-testkit`: starts ImapKit (`core/e2e`) for the end-to-end tests and talks to its REST API.
- `pe-ffi`: the only crate with `unsafe` code and the only one the app links. Every other crate starts with `#![forbid(unsafe_code)]`.

### The C ABI (`pe-ffi`)

- Built as `staticlib` (`pe_ffi.lib`) and linked into the exe, not as a DLL: one signed exe, no DLL search-order risk.
- `build.rs` runs cbindgen and writes `core/include/inbox_classic.h`. The header is committed so API changes show up in diffs; rebuild the crate after changing an export and commit the header with it.
- Calls are coarse, on opaque handles. Strings go both ways as UTF-8; strings returned to C++ are allocated by Rust and released with `pe_string_free` (in C++, `core::String`, a `unique_ptr` with that deleter, see `app/src/core.h`).
- Lists and views are opaque handles holding `repr(C)` rows whose strings they own (`pe_folders`, `pe_folder_list_get`, `pe_folder_list_free`). No JSON: C++ parses nothing. Enum constants are qualified (`PE_SORT_FIELD_DATE`) by `cbindgen.toml`.
- Work that touches the network runs on the workers and reports through the event callback, on a worker thread: the C++ callback copies the event, posts it to the window thread, and must not throw.
- Every export runs its body inside `guard` (`catch_unwind`) so no panic crosses into C++. Do not switch to `panic = "abort"`: a panic on a malformed message would then crash the app on every start.
- Rust is built with `+crt-static` (`core/.cargo/config.toml`) to match the static CRT of the app (`/MT`, no Debug CRT variant). Cargo only reads that file when it runs in `core/`, which is why `app/CMakeLists.txt` sets `WORKING_DIRECTORY`. When a new Rust dependency needs more Windows system libraries, get them from `cargo rustc -p pe-ffi --release -- --print native-static-libs` and add them to `target_link_libraries`.

## C++ app (`app/`)

Plain Win32 (C++20, MSVC, `/W4 /utf-8 /permissive-`). The manifest (`app/res/app.manifest`) deliberately has no dependency on Common Controls 6, so the controls draw in the classic 3D style; keep it that way. Code style and patterns (pages, dialogs, tray, list views, preview) follow `../imapkit-win/host-win/src`; borrow from there when adding UI. CMake runs `cargo build --release --locked -p pe-ffi` on every build, with the Cargo target dir under `build/cargo`, and downloads the WebView2 SDK from NuGet pinned by hash.

Toolbar icons are Fluent UI System Icons (MIT): the SVGs in `app/res/icons`, turned into bitmap strips (`app/res/toolbar`: Fluent's own 16 and 20 pixel designs for the small sizes, each drawn over what is behind it, the button face for the toolbars and white for the tree and list, which is then its transparent color, as the classic image lists have no alpha) with `app/res/toolbar.rc` (their resources) and `app/src/icons.h` (their order and sizes) by `scripts/build-icons.sh` (rsvg-convert and ImageMagick). These are committed; run the script after changing an icon or the lists in it, and check the result on a screenshot. The app icon and the logo come from `design/logo` (its README says which file goes where): `app/res/app-icon.svg`, `app-icon-small.svg` for 32 pixels and below and `app-icon-mac.svg` for the Mac, which `build-icons.sh` and `mac-build.sh` turn into `app.ico`, the Linux tray pictures and the .icns. The Google and Microsoft sign-in buttons of Add Mail Account are the providers' own pictures (`app/res/brands`); `scripts/build-sign-in-buttons.sh` makes them in each language (`google-sign-in.de.png`, the label from `win-sign-in-google` in the providers' fonts), and `pe_localized_picture` picks the one of the language in use.

The app version is the `[workspace.package] version` of `core/Cargo.toml`. CMake reads the first `version = "x.y.z"` line of that file, so keep `[workspace.package]` at the top.

## Three apps

Windows (`app/`, C++ and Win32), the Mac (`mac/`, Swift and AppKit on the C API) and Linux (`linux/`, Rust and GTK 4 on `pe-core` directly) are three thin windows on the one core. `docs/shells.md` says where each feature lives on each; `docs/cross-platform-plan.md` is the plan they were built from.

- **A feature lands on all three in the same pull request.** The order of work: the core and its tests; `core/commands.toml` (a command of the menus) or the C API; the three apps; the step in `scripts/ui-e2e/SCENARIO.md` and in each platform's UI end-to-end test, and its entry in `scripts/feature-map.mjs`; the help (the topics of `core/crates/pe-html/help/<lang>/`, `<!--os:mac-->...<!--/os-->` where the platforms differ). `scripts/check-shells.sh` fails a PR that changes the C API, the commands or the feature list without changing `app/`, `mac/` and `linux/`, unless it is labelled `shells: partial` and says what is left; `feature-map.mjs --check <platform>` fails a platform whose test does not show a feature, unless `notYet` lists it.
- **The core computes, the apps show.** Every string, count and decision from mail data comes from the core (sizes, account labels and folder names are in `pe-core/src/text.rs`); an app reads values and calls operations. Logic needed by all three goes in the core once.
- **Commands** come from `core/commands.toml`: generated into `core/include/commands.h`, `mac/Sources/InboxClassic/Generated/Commands.swift` and `linux/src/generated/commands.rs` by pe-ffi's `build.rs` (committed; CI checks they match). Each app handles the enum in one exhaustive switch, so a new command fails the build of an app that does not handle it.
- **Web views**: WebView2 serves the documents at `https://*.inboxclassic.invalid/`, WKWebView and WebKitGTK from the scheme `inboxclassic:`; all three block every other load (WebView2 by its request filter, WebKit by `pe_webkit_content_rules`), and only the editor page runs a script.
- **The Mac**: `scripts/mac-build.sh` builds `build/mac/Inbox Classic.app` (Swift package in `mac/`, no Xcode project; Sparkle 2.10 from its release in `build/sparkle`; ad hoc signed, no hardened runtime), `scripts/mac-ui-e2e.sh` runs its UI test, which hosts the app in-process and drives its windows (no accessibility or screen recording permission needed; the system's file panels are answered by `TestHooks`), screenshots in `build/ui-e2e-mac`. `scripts/mac-package.sh` makes the signed, notarized `dist/InboxClassic.dmg`. The core's events reach the windows through run-loop blocks in the common modes (`onMain` in `Core.swift`), never `DispatchQueue.main`, whose blocks stop while a modal window runs.
- **Linux**: `scripts/linux-build.sh`, `linux-test.sh`, `linux-ui-e2e.sh` and `linux-package.sh` run in Docker (`linux/Dockerfile`, Ubuntu 26.04; arm64 natively, amd64 through Rosetta); the UI test is built in with the `e2e` feature and runs under Xvfb, screenshots in `build/ui-e2e-linux`. `scripts/linux-vm.sh` runs an Ubuntu Desktop VM in QEMU for what only a desktop shows (the tray, notifications, the dock). Arch Linux: `linux/arch/PKGBUILD` builds from the release's source; Omarchy's package repository (`omacom-io/omarchy-pkgs`, `pkgbuilds/inbox-classic`) builds it from each release by itself (an upstream watch on our GitHub Releases), so a release needs no Arch step. `scripts/arch-package.sh` builds and checks it for x86_64 and aarch64 in Arch containers with `scripts/arch-makepkg.sh`, which CI's `arch` job runs too (`--release` builds the release's own tarball and writes the recipe with its checksum to `dist/arch/inbox-classic/`), CI's `arch` job also runs the UI test on current Arch, and `scripts/omarchy-vm.sh` runs an Omarchy desktop in VMware on the Windows build machine (installed unattended from the official ISO, reached over SSH through that machine, screenshots with `grim` in the guest).
- **The homepage** shows each visitor their platform's download and screenshots; `scripts/homepage-screenshots.sh` refreshes the screenshots of all three from the UI tests' runs.

## Commands

Rust, on the Mac or anywhere:

```
cd core
cargo test --workspace                 # all tests
cargo test -p pe-html keeps_mail_layout   # one test
cargo clippy --workspace --all-targets
cargo fmt --all
```

`Cargo.lock` is committed and the Windows build uses `--locked`, so commit lockfile changes along with dependency changes.

The app only builds on Windows. The build machine is `andri@10.8.0.8` (Windows 11, VS 2022 Build Tools, Rust via rustup); the sources live at `C:\Users\andri\src\postal-express`. From the Mac:

```
scripts/win-build.sh                  # copy the working tree over (tar, no .git or build outputs) and build build\InboxClassic.exe
scripts/win-test.sh [cargo args]      # copy and run cargo test on Windows
scripts/win-run.sh                    # start the app on the interactive desktop (scheduled task; SSH has no desktop)
scripts/win-screenshot.sh out.png     # screenshot of the window, DESKTOP=1 for the whole screen
scripts/win-ui-e2e.sh                 # the UI end-to-end test on the desktop, log and screenshots in build/ui-e2e
```

To drive the UI for a check, run these on the build machine through a scheduled task (`/it`, as `win-run.sh` does): `scripts/ui-account.ps1` fills both steps of the Add Mail Account form (use an Ethereal account), `scripts/ui-select.ps1 <folder> <row>` selects a folder and a message.

`scripts/ui-e2e.ps1` is the end-to-end test of the app itself: it starts ImapKit and the exe (with `--store`, `--memory-passwords`, `--pin-certificate` for ImapKit's self-signed certificate and `--sign-in-page-file`, where a browser sign-in writes its page for the test to open in place of the browser), adds the account through the form, reads, replies and opens the help, checking the results over ImapKit's REST API. CI runs it after the Windows build. `node scripts/feature-map.mjs [dir] [out.html]` turns its screenshots into a page that maps every feature to its screenshot; update the feature list there when features change. It finds controls by the ids in `app/src/app.h` and the form order in `accounts.cpp`, so update it when those change. The user help is one topic a file, `core/crates/pe-html/help/<lang>/<id>.html` in the markup of `help/FORMAT.md`, ordered by `help/topics.toml` (`<!--os:mac-->...<!--/os-->` marks a part for some platforms only; keys come from `core/commands.toml` and control names from the catalogs, so neither is written by hand); `pe-html` `help.rs` makes each platform's pages: Windows' help window and Linux's (`pe_help_topic`, `pe_help_contents`, `pe_help_search`), the Mac's Help Book (built by `mac-build.sh`), Yelp's pages (installed by the Linux packages) and the website's (`scripts/homepage-help.sh`, run by the release). F1 opens the topic of the window it is pressed in (`help/topics.toml` `[context]`). Update the help with the features it describes, in every language (the translations marked for review).

`PE_NETWORK_TESTS=1` enables the tests that need the internet (`pe-autoconfig/tests/live.rs`); CI sets it on Linux.

Releases: release-please keeps a release PR on master (`release-please-config.json`, `.github/workflows/release.yaml`, which also updates `core/Cargo.lock` and `linux/Cargo.lock` on it and the version in `linux/Cargo.toml`); merging it drafts the release and pushes the tag, then `scripts/release.sh` on the Mac, from the tag, builds the Windows installer (on the build machine), the Mac disk image (signed and notarized) the two Linux packages (in Docker; the apt repository gets them) and the two Arch packages (`scripts/arch-package.sh --release`, from the release's tarball; Omarchy's package repository builds its own from the tag), starts each with `--version`, writes a GPG-signed `hashes.txt`, uploads them and publishes the draft, then puts the Mac update (Sparkle's `appcast.xml`, signed with the key `generate_keys --account inbox-classic` keeps in the release Mac's keychain) on the homepage. `PLATFORMS=mac` rebuilds one platform to finish a release one of whose builds failed. The homepage links `releases/latest/download/` `InboxClassic-Setup.exe`, `InboxClassic.dmg`, `InboxClassic-amd64.deb`, `InboxClassic-arm64.deb` and, in `curl -LO` and `sudo pacman -U` for Arch and Omarchy, `InboxClassic-x86_64.pkg.tar.zst` and `InboxClassic-aarch64.pkg.tar.zst`.

`scripts/build-installer.sh` builds `dist/InboxClassic-Setup.exe` (NSIS, `installer/inbox-classic.nsi`, per user, no admin rights) with `THIRD-PARTY-NOTICES.txt` from `scripts/notices.mjs`; it signs the exe, the uninstaller and the installer with Azure Artifact Signing (`scripts/sign-win.sh`) when `SIGN_WIN_ACCOUNT` and `SIGN_WIN_PROFILE` are set.

On Windows itself: `scripts\win-build.cmd` and `scripts\win-test.cmd`. Both call `scripts\vcvars.cmd`, which finds Visual Studio with vswhere and puts cargo on PATH.

Screenshots need a logged-in desktop session that is not disconnected or locked; check with `ssh andri@10.8.0.8 query user` (`Active`, not `Disc`). In a disconnected session they come out blank white.

CI (`.github/workflows/ci.yml`) runs fmt, clippy with `-D warnings`, a check that the committed C header and command tables match the build, the Rust tests on Linux, Windows and macOS, and each app's build and UI end-to-end test with its feature check: Windows (artifact `InboxClassic-win-x64`), the Mac on `macos-26` (`InboxClassic-mac-arm64`, signed ad hoc), Linux in an `ubuntu:26.04` container (`InboxClassic-linux-amd64`); on pull requests also `scripts/check-shells.sh`. Markdown and YAML are formatted with prettier (`npx prettier --write`, config in `.prettierrc.json`).

For test IMAP and SMTP accounts use Ethereal (see the global instructions) or ImapKit (`../imapkit`, `../imapkit-win`).
