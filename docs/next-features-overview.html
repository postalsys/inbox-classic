2. Conversations

The core builds the conversations and hands the apps a flat list in which each row says its depth, whether it has replies and whether it is open. The apps only draw an indent and a +/- button, so their virtual lists keep paging by offset as they do today.

  • Fetch References with every summary; a background pass fills it in for stored mail, newest first. In-Reply-To, already stored, covers most replies meanwhile.

4. Bounces explained

bounce-classifier classifies one SMTP reply, not a whole message, so the port has two halves: finding the bounce and its recipients, codes and server words (EmailEngine's lib/bounce-detect.js, 1,200 lines), and classifying each server reply into one of 16 labels (bounce-classifier, a 325,000 weight network with rules on top). Both port cleanly to Rust: the network is an embedding lookup, an average and two small dense layers.

Six pictures cover the 16 labels:

11
pe-bounce (core only) M
  • detect.rs: RFC 3464 delivery-status per recipient, X-Failed-Recipients, Gmail, Exchange, Postfix, Exim, qmail, WorkMail and Zoho formats, delay told from failure, the original message's headers. Heuristics only for mail from mailer-daemon or postmaster or with Auto-Submitted.
  • classify.rs: tokenizer with ASCII \w as in JS, the forward pass, the text and SMTP code rules, retry timing, blocklist names. Model files built in with include_bytes!; scripts/update-bounce-model.sh refreshes them.
  • Conformance against the JS output (labels, scores to 1e-5, fields found) over both projects' fixtures, as pe-content does; EmailEngine's hostile input tests ported. Rust's linear-time regex removes the ReDoS risk.
12
The card in the reading pane M
  • view.rs finds the bounce when the message is opened; pe-html draws the card: failed or delayed, each recipient with a plain explanation and what to do, the server's words escaped under Details, the blocklist named with a link to its own removal page (from a fixed table, never from the message).
  • "Show the message that bounced" when it is in Sent Items. 16 explanations in core.ftl, in five languages.
  • In the list: an "undelivered" icon for messages whose BODYSTRUCTURE is multipart/report with delivery-status (marked at sync, a migration fills stored mail), and is:bounce in the search.

How each pull request is done

  1. On master, git pull, then a branch feat/<name>.
  2. The core and its tests first: unit, migration, and e2e_core against ImapKit for anything that talks IMAP.
  3. commands.toml or the C API; rebuild pe-ffi, commit the header and generated command tables.
  4. Windows, the Mac and Linux.
  5. Translations: English, then draft German, Estonian, Spanish and French per GLOSSARY.md, each draft marked for your review (below); the pe-i18n tests; a pseudo-language run for leftovers and cut-off text.
  6. Help in all five languages, the key table included; docs/shells.md.
  7. UI end-to-end: the step in SCENARIO.md and all three tests, screenshots in feature-map.mjs; run the three locally, look at the pictures, --check each platform.
  8. UX and design review, repeated until nothing is left to improve: for every visible change, review the screenshots of all three platforms (English and pseudo-language, light and dark) as a UX designer and mail app product expert: layout, spacing, wording, control and menu order, keyboard use, what a new user expects, and how Outlook Express, Thunderbird and Apple Mail do it. Improve, take new screenshots, review again; stop only when a round finds nothing. The rounds go in the PR description; fixes are committed as fix(ux), in the platform's own look. The rounds run on the Mac and Linux screenshots; Windows follows (below).
  9. /simplify, with the maintainability check on the functions that grew.
  10. /security-review; fix what it finds.
  11. cargo fmt, clippy -D warnings, cargo test --workspace, prettier, check-shells.sh.
  12. Commits in order: feat(core), feat(windows), feat(mac), feat(linux), feat(i18n), docs(help), test(e2e), then fix(ux), refactor and fix from the reviews.
  13. Push, open the PR, watch CI; fix real failures, rerun flaky jobs at most three times.
  14. Merge with a merge commit once CI is green and the last design review round found nothing to improve, without waiting for a review; the next PR starts from the new master.
