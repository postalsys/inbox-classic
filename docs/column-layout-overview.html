A column layout for wide windows

Three panes side by side on a large monitor, the classic layout on a small one, picked by the window's width unless you choose. With it: a folder list that can be hidden, message rows of three lines, and the sender's picture. The full plan is docs/column-layout-plan.md; nothing is started.

In one line: View > Layout gets Automatic, Classic and Columns. Automatic turns to Columns at 1320 pixels of width and back to Classic under 1200. Classic stays exactly as it is today.

Try it

Drag the width, or pick a layout. The toolbar's small button hides the folder list. This is a sketch of the idea, not of any platform's look: Windows keeps its classic controls, the Mac and Linux their own.

Classic or Columns, decided by width

Classic
under 1200
keeps what it has
Columns
1320 and wider
  • One rule in the core (layout_for), in platform-independent pixels, so the three apps switch at the same widths.
  • No flicker at the line. Between 1200 and 1320 the window keeps the layout it has, so dragging its edge near the line does not flip the panes back and forth.
  • Your choice wins. Classic or Columns picked in View > Layout (or Options) stays. An explicit Columns holds down to 900; narrower, the window shows Classic without changing the setting.
  • Switching loses nothing: the selection, the focus, the open conversations and the selected row stay in view. Each layout remembers its own pane sizes.
  • Only the reading pane grows. In Columns the folder list and the message list keep their widths when the window gets wider; the message gets the rest. Plain text gets a line length limit (about 46em), so a 2000 pixel pane does not make 300 character lines.

Hiding the folder list

A command of its own (View > Folder List, with a check mark), in both layouts, remembered. Each platform gets the button its users know:

A row of three lines

JKJaan KaskTueRe: Lunch on Thursday?Works for me. The place by the harbor again?
  • Line 1: who (bold while unread) and a short date: the time today, the weekday this week, day and month this year. Sent and Drafts show "To:" and the recipients.
  • Line 2: the subject; attachment and flag marks at the right.
  • Line 3: the first words the sender wrote, without the quoted reply; the conversation's count and opener at the right.
  • Left: the unread dot and the picture.
  • Fixed height, so the list stays fast and nothing jumps when the text arrives.
  • No column headers: "Sorted by Date ▾" above the list, and View > Sort By in both layouts.
  • Classic rows do not change: one line, columns, no picture.

The text line is new data. The core stores no message text it can read back today (the search index is one way). A new messages.snippet is written where the text is already at hand, so new mail costs no extra download. Mail stored before is done from downloaded sources, the rest in a background pass, newest first.

Whose picture

One picture a row, chosen by the core in this order:

N
First

The brand's logo (BIMI)

When the mail provider's own check says the logo and the sender are genuine. The rule the reading pane uses today.

AL
Then

The contact's picture

Set in the Address Book (Choose…, or drop a file). Shown only when the message is confirmed to come from that domain, never in Junk E-mail.

JK
Else

Quiet initials

One muted tone for everyone, no color per sender, so real logos and faces are what the eye finds.

  • Why confirmed only: a contact's picture is matched by an address, and a From address can be forged. A fake "boss@company.com" must not get the boss's face.
  • Logos are downloaded once a domain and kept for 30 days, never a message at a time, so a logo's address cannot be used to see who opened what.
  • Pictures are decoded in Rust only. The apps get pixels, as they do for the logo today. A vCard's embedded photo is imported; one that is a link is never fetched.
  • The reading pane shows the contact's picture where it shows the logo today. Options gets "Show senders' pictures in the message list".

What changes where

Core

  • layout_for and its numbers
  • Commands: three layouts, Folder List, Sort By
  • Migration 23: the text line, the sender's verdict, kept logos, contact pictures
  • Three header fields fetched with the summaries
  • pe_picture_start, pe_card_set_picture

Windows

  • Layout() with a mode; a vertical second splitter
  • The list made again as owner drawn for Columns (a spike first)
  • Window place and splitters remembered, a minimum size
  • "Folders" caption, the folder bar's drop-down

Mac

  • rightSplit.isVertical follows the layout
  • One column, no header, a new row cell, as Mail's column layout
  • A collapsible sidebar with its toolbar button

Linux

  • The paned's orientation follows the layout
  • A ListView beside the ColumnView, on the same model
  • The narrow window's breakpoints stay as they are

Risks

  • Windows' owner drawn list is the one unknown (owner draw together with a virtual list, the keyboard, screen readers). Half a day's spike first; the fallback is a tall image list with custom draw.
  • Fewer logos than Gmail's own page shows: Gmail does not expose its BIMI verdict in the header the app trusts. Looking the record up ourselves would trust any domain's own claim without checking its certificate, so it is left out.
  • A larger first sync: three more header fields a message. To be measured on a large folder before step 4 lands.
  • The UI tests: Linux's test window is 1600 wide, so the existing steps pin Classic at their start, or Automatic would turn every existing screenshot into Columns.
