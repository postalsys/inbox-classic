OpenPGP in Inbox Classic

Encrypted and signed mail, done entirely inside the app: the Rust core parses, checks, decrypts and signs, and the three apps show what it decided. Eleven pull requests, each on Windows, the Mac and Linux at once, released together at the end.

15 November 2026 · from 0.18.0 · the full plan is pgp-plan.md beside this page · the work starts when you say go

Decided

  • A master key in the keychain. Private keys are kept wrapped under it in the local store. An imported key's passphrase is asked once. No prompts after that.
  • Encrypt and Sign are manual, off for a new message, nothing remembered. A reply to encrypted mail starts encrypted.
  • Keys are looked up only when Encrypt is turned on, or with Find Key: the domain's Web Key Directory first, then keys.openpgp.org.
  • Colored frames, a document for each part: labels and mail never share a document, so a sender's CSS can not touch a label. The bar sums the parts up.
  • Fallback if heights can not be measured with scripts off: one part at a time, from a native strip.
  • Only protected mail is drawn this way; a message protected as a whole gets the bar and one label.

Decided, continued

  • Two levels of trust: a found key is usable and shows blue; a key whose fingerprint you compared shows green. A new key for an address is never taken silently.
  • Autocrypt, read and sent, never asking others to encrypt by default.
  • Decrypted text is indexed for search and snippets (a switch in Options); the message stays encrypted on disk.
  • Protected headers are read, not written: outgoing mail keeps its Subject as written.

Defaults I chose (say if otherwise)

  • rPGP as the library: MIT, pure Rust, audited. The policy layer is ours; Sequoia checks our output in CI.
  • New keys: Ed25519 and Curve25519, version 4, no expiry.
  • Encrypt always signs and always includes your own key.
  • No half encrypted mail: Send stops if someone has no key.
  • Inline PGP: decrypted, its signatures not checked.
  • Internet pictures in decrypted parts only on a click, never remembered; after it the part no longer says "Encrypted".
  • Agents see no decrypted mail and can not sign or encrypt.
  • A backup is offered right after a key is made.

How a message with several parts is drawn

Each part is decrypted or checked by itself and is a document of its own, in a sandboxed iframe. The labels are in an outer page the core makes, which holds no markup from mail. The bar is native and counts the parts.

Encryption adds a lock and "Encrypted" to the label. A part whose integrity is not protected is not shown at all. A failed signature never looks more dangerous than unsigned mail (RFC 9787).

A document for each part

  • The outer page holds no mail markup: only the core's labels and one iframe a part.
  • A part can not draw outside its iframe: the browser's rule, not our CSS. Each has its sandbox, CSP and picture rule.
  • Label words come from the core: the checked address and your Address Book's name, never the key's own name.
  • Heights are measured by a script the app runs while page scripts stay off. A spike on the three web views comes first; if it fails anywhere, all three show one part at a time from a native strip.
  • Select All, Copy and Find work inside one part; print gets one document.

What remains: a look-alike painted inside a sender's own part, under its real label, or in a message with no layer and no bar.

The rules behind a verdict

  • The whole message's state comes from the layers at its top only (RFC 9787); any other layer is just a part.
  • A signature counts for the sender only if the key has a user id with the address of the one From.
  • Validity is judged at the time of signing; MD5 never, SHA-1 only for old signatures, RSA from 2048 bits.
  • Integrity first: no plaintext leaves the engine before the check passed.
  • Replies quote only what was shown; nothing is decrypted for a reply.

Private keys without prompts

System storeKeychain, Credential Manager or Secret Service holds one random 32 byte master key, beside the mail passwords.
Local storeEach private key wrapped with ChaCha20-Poly1305, bound to its fingerprint and the profile.
In useUnwrapped for one operation, wiped after it. Nothing decrypted stays in memory.
ImportThe key's own passphrase is asked once and not kept.
BackupOffered at once: the key under a passphrase you choose. The only passphrase ever typed.
No system storePublic keys only, and the app says so. A reset keychain means importing the backup.

Why not the key itself in the system store: Windows Credential Manager takes 2560 bytes an entry, less than an RSA 4096 private key.

The parts

1. The engine

LPR 1

A new crate, pe-pgp: pure functions over bytes on rPGP, no network, no files, no unsafe code of ours. Today the code base has no OpenPGP at all; a signed message shows its signature as an attachment and an encrypted one shows nothing.

What it holds

  • Certificates: parse, merge, minimize, validity at a given time.
  • The policy, one table: what is acceptable and since when. rPGP has none, so it is ours.
  • Verify, decrypt (integrity mandatory, limits on size and nesting), sign, encrypt, generate, passphrase protection for import and backup, the Autocrypt header.
  • A sop command line on the same functions, for the cross-checks.

Tests

  • RFC 9580's vectors; fixtures made by GnuPG, Sequoia and OpenPGP.js.
  • One test a row of the policy; one for each rPGP advisory of 2024 to 2026.
  • Three fuzz targets.
  • CI: our sop against Sequoia's, both directions, on every PR; the OpenPGP interoperability suite on a schedule.

2. Keys

LPR 2PR 3

My Keys

  • Tools > Encryption Keys, and a Security page in Account Properties: one key for each own address, aliases included.
  • New Key, Import, Save a Backup, Export Public Key, Publish, Remove.
  • Import from a file, the clipboard, a key attached to a message (a card with Import), a vCard.

The Address Book

  • A contact's window lists the keys of its addresses: fingerprint, where it came from, Verified or not.
  • Find Key, Import, Verify (both fingerprints side by side), Export, Remove.
  • A small key in the list for people who have one. vCard import and export carry KEY.

A changed key

  • Another key for an address that has one is kept waiting: "A new key was found for a@example.org on 3 December", Use the New Key or Keep.

Tests

  • A wrapped key does not open with another master key, profile or row; the database file never holds a private key.
  • The real system stores on the three systems (PE_KEYRING_TESTS=1).
  • UI: keys-1 to keys-8, with the case of no keychain on Linux.

3. Reading

LPR 4PR 5

How it is built

  • pe-mime gets outline: the tree of parts with their byte ranges in the source. A signature is checked over exact bytes, which the parser does not keep today.
  • pe-core cuts the message into sections, gives each a verdict; pe-html makes the outer page and each part's document; the view carries the summary for the bar.
  • The bar sits where Outlook Express had its ribbon and lock, on all three.
  • Inner Subject and addresses of protected headers are shown when their layer is valid.

Tests

  • A corpus of mail with the expected verdict of each: ordinary mail of seven clients, parts signed apart, EFAIL, "Johnny, you are fired", "Re: What's up Johnny", inline PGP, deep nesting.
  • The spike first. The outer page holds nothing from a message but escaped label words, tested with hostile key names.
  • Fuzz targets for the outline and the whole reading path.
  • UI: secure-1 to secure-10, the mixed parts and the fake frame among them, light and dark.

4. Writing

LPR 6PR 7

How it behaves

  • Sign and Encrypt in the compose window, both off. Encrypt turns Sign on and needs a key for the From address.
  • With Encrypt on, each recipient shows a lock or a warning; Send stops with the list of who has no key.
  • The Sent copy is readable through your own key; drafts go to the server encrypted to it, unsigned.
  • Bcc recipients are not named in the encrypted message.
  • Removing Encrypt from a reply that quotes encrypted text is refused until the quote is gone.
  • Attach My Public Key.

How it is built

  • One place turns a message into bytes (worker::build); the protection goes there. pe-smtp builds the content apart and wraps it; ordinary mail is byte for byte as before.
  • Undo Send and reopening a draft go through the reading path.

Tests

  • OpenPGP.js as the other person in the ImapKit harness: it checks what we send and writes what we receive.
  • The message on the server holds none of the text's words; UI: write-30 to write-35.

5. Finding keys

MPR 8

How it behaves

  • The local keys, then the domain's Web Key Directory (only the recipient's own provider learns of it), then keys.openpgp.org.
  • Only for a message being encrypted, or Find Key. A miss is remembered for a day. A switch in Options turns keys.openpgp.org off.
  • A key is taken only if it names exactly the address asked for; it starts as "found", not verified.
  • Publish: upload and ask for the confirmation mail, which lands in your own inbox.

Tests

  • A loopback server playing both: found, 404, 429, 503, too large, a redirect, the wrong address, extra user ids.
  • One live lookup each with PE_NETWORK_TESTS=1.
  • UI: keys-9 to keys-11, write-36.

6. Autocrypt

MPR 9
  • Read whenever a message is parsed: one From, the header's address equal to it, not Junk, not a report; ordered by date.
  • Sent from an address with a key, unless turned off in Account Properties.
  • Gossip of the other recipients' keys only inside encrypted mail.

Tests

  • Autocrypt's own examples; the rules one by one; both directions with OpenPGP.js; UI: keys-12, keys-13.

7. Search, the list, notifications, agents

MPR 10
  • A lock or ribbon in the message list; is:encrypted and is:signed.
  • Decrypted text is indexed when a message is opened, or in the background once its source is cached. The switch off removes it.
  • A notification says the sender and "Encrypted message".
  • Agents: text that came from decryption is marked, and their list, search and read leave it out.

Tests

  • Found by a word of its text after the background pass, not after the switch is off.
  • The agents' tools never return decrypted words; none signs or encrypts.

8. Hardening

MPR 11
  • /security-review of everything since 0.18.0 as one piece, and the security audit skill over the engine, the reading path, the key store and the frames, with the threat table as its checklist.
  • Every fuzz target run for an hour; the interoperability suite's report read, failures fixed or listed with the reason.
  • /simplify over the feature as a whole; the help complete in every language; CLAUDE.md gets the new crates and rules.

How every PR is done

  1. A branch in a worktree of its own, from an updated master.
  2. The core and its tests: unit, corpus, migration, ImapKit end to end.
  3. Commands or the C API, the header committed; then the three apps.
  4. Translations in five languages, marked for review; the help in each.
  5. UI end to end on the three platforms, the feature map, the screenshots looked at.
  6. UX review until a round finds nothing; here also: can every state be told from every other without color?
  7. /simplify over the changed code, with the maintainability check.
  8. /security-review of the branch; fix what it finds and go on.
  9. fmt, clippy, the tests, prettier, check-shells.sh; push, watch CI, merge when green.

Not in this round

S/MIME, smartcards and hardware keys, post-quantum keys, the Autocrypt Setup Message, loose .pgp files attached to ordinary mail, encrypting the Subject of outgoing mail.
