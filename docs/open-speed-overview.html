Opening messages faster

Why a new message often shows a spinner when it's opened, what other mail clients do instead, and a plan in six phases to make opening instant in the usual case.

In short. The app already gives opening a connection of its own, so a click never waits for a sync. The waiting comes from three things:
  1. Nothing is downloaded before the click.
  2. That connection goes stale between clicks, and a dead one is only noticed after 5 minutes.
  3. Large messages show nothing until every attachment has arrived.
Other mail clients download new mail as it arrives and keep their connections warm. The plan does both, and puts the user's request ahead of background work.

What other mail clients do

Apple MailDownloads new messages in full as they arrive, attachments too by default. Opening reads from disk.
ThunderbirdKeeps IMAP mail offline by default and downloads bodies in the background. It keeps several connections per server (5 by default), fetches only the parts it shows first for large messages it isn't keeping, and renders while streaming.
OutlookCached mode: a local copy of the mailbox that syncs in the background. The user works on the copy.
Mobile clientsGmail, K-9 / Thunderbird for Android and iOS Mail download recent mail up to a size limit, and the rest of a large message when it's opened.
Gmail, Fastmail (web)Load the messages near the one on screen, so Next opens at once. Actions show immediately and reach the server after.

Five things they have in common:

  1. The body is there before the click, which is the main reason they feel instant.
  2. The user's request jumps the queue.
  3. Connections are kept warm, and replaced after sleep or a change of network.
  4. What can be shown is shown first: the header at once, then the text, then the attachments.
  5. Neighbors are fetched ahead, because the next click is usually Next or the row below.

The plan

All of it is in the core, so the Windows, Mac and Linux apps get it at once. The apps change only to report sleep and network changes (phase 2) and to show one new setting (phase 3).

Phase 1

Measure small

  • Timing for every open: queued, connect, sign-in, SELECT, first byte, last byte, store write and view. Each record also has the size and whether the connection was new, reused or retried.
  • Kept in memory for the last 200 opens; any open over 1 s goes to the log (no message content).
  • An open-timing example against ImapKit with latency injected, run before and after each phase.
Phase 2

A reader that is always ready small to medium

  • Connect it at start, not at the first click.
  • A NOOP every 4 minutes while it waits; TCP keepalive on every socket.
  • After a minute unused, a 3 s NOOP check before the FETCH.
  • An 8 s limit for the first byte of what the user waits for, then a fresh connection. The 300 s limit stays for background work.
  • The apps report waking from sleep and network changes; the core then drops its connections and connects the readers again.
  • Fix the code_of_new timeout.
Phase 3

The message is here before the click medium

  • New mail is downloaded in full as it arrives, if it's under the size limit. That's one FETCH in the same session, and the folder is already selected.
  • The search's background text download fetches whole sources instead, so those messages open instantly too.
  • After an open, the reader also fetches the message above and the one below in the list.
  • A new setting for the whole app, with a storage limit for each account.
Phase 4

The user goes first medium

  • A second reader connection when a click comes during a large download.
  • Background batches wait while an open is under way, and are sized by bytes (about 512 KB) so a move or delete starts quickly.
  • The view is built from the downloaded bytes and the store is written after.
Phase 5

Large messages show text first large

  • Over 1 MB: the structure, text parts and inline pictures come first, then the view is shown. The attachments are listed from the structure.
  • The whole source follows in the background. Save As, View Source, Forward and opening an attachment wait for it, with progress shown.
Phase 6

Waiting that says something small

  • The spinner appears after 250 ms on every platform, not just Windows.
  • After 1 s the pane shows how much is left: "Downloading 4.2 of 15 MB".
  • The UI tests check that a prefetched message opens without the downloading state ever showing.

The new setting (phase 3)

One setting for the whole app: in Settings on the Mac and Linux, in Options on Windows.

Past it, the oldest messages' copies are removed first (never Drafts or the Outbox). They download again when opened.

Tests

  • pe-imap:
    • the first byte limit;
    • a server that answers nothing (the UI test's SilentServer);
    • keepalive set on the socket.
  • pe-core with ImapKit:
    • new mail arriving over IDLE is in the store without an open, and messages over the limit are not;
    • an open also fetches the neighbors;
    • a cut reader connection recovers within the first byte limit;
    • a second click during a large download is answered first;
    • background batches wait during an open.
  • UI tests, all three apps:
    • a new message opens without the downloading state;
    • an open after ImapKit closes the session still succeeds;
    • the new setting.
  • The timing example: numbers before and after go in each pull request.

How each phase lands

Each phase gets one branch and one pull request off an up-to-date master, and is merged only when CI is green.

  1. Build. The core and its tests, then the C API and the three apps, then the UI tests, SCENARIO.md, feature-map.mjs and the help in every language.
  2. Check locally. cargo fmt, clippy, cargo test --workspace, the Linux checks, and the UI tests of the apps the phase changes. The timing example runs before and after, and its numbers go in the pull request.
  3. /simplify on the diff, and its findings applied.
  4. /security-review on the diff, and its findings fixed. Phases 3 and 5 get extra attention. Mail downloaded ahead is untrusted, and it is stored and parsed without the user opening it. A partial message must never be taken for a whole one.
  5. Tidy. Prettier on Markdown and YAML, and the translation check where words changed.
  6. Push and watch CI. A real failure gets fixed and pushed again. A flaky one is rerun, at most three times.
  7. Merge when CI is green, then start the next phase from the new master.

A release isn't part of this plan; one is cut when you ask.

Decided

  1. Downloading ahead: recent messages (the last 30 days) up to 1 MB by default.
  2. Storage: a limit you set, applied to each account (1 GB to start).
  3. Phase 5: built now, as part of this plan.
  4. The setting: one for the whole app, not per account.
  5. Pull requests: one per phase, merged when CI passes.
