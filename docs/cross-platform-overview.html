Plan, 2026-11-04, from version 0.4.1, decisions confirmed

Inbox Classic on Mac and Linux

A Mac version and a Linux version are possible, and most of the work is already done: everything that handles mail lives in the Rust core, which builds and passes its tests on all three systems today. Each new platform needs a native shell of about the size of the Windows one, a password backend, a build and release path, and, once there are three shells, a way to keep them in step. The full plan is in docs/cross-platform-plan.md.

One core, three shells

The core is the only place that parses anything a remote party wrote. A shell draws, wires and calls; it never derives. The Windows shell talks to the core through the C ABI of pe-ffi, the Mac shell does the same from Swift, and the Linux shell, being Rust, links pe-core directly.

Targets

Current releases only. Nothing older is supported, which keeps each shell on one toolkit version and one set of APIs.

Windows

  • Windows 10 and 11, as today
  • Nothing changes but the shared pieces: the command table, the help filter, pe_format_size

macOS

  • macOS 27 (2026-09-14, Apple silicon only), built with Xcode 27 on this Mac, which runs 26.6.2
  • Deployment target 26 until this Mac moves to 27; arm64 only, no universal binary
  • Swift 6.4, AppKit, WKWebView; Developer ID signing and notarization; Sparkle updates

Linux

  • Ubuntu 26.04 LTS and newer (26.10 is out), GNOME 50 on Wayland, x86_64 and arm64
  • GTK 4.22, libadwaita 1.9, WebKitGTK 2.52 (the 6.0 API), as 26.04.1 ships them
  • Rust with gtk4-rs, a .deb first, Flatpak second

The web views, locked down three ways

The one real porting risk. WebView2 lets the C++ refuse every request on *; WebKit cannot intercept https, so the WebKit shells serve the documents from a custom scheme and block everything else with a content rule list, which the core generates once and Rust tests pin. The Mac spike in week 1 settles whether this holds, with a hostile test message that every platform's end-to-end test keeps checking.

Releasing on three platforms

Every release is built from the release Mac, as today, and nothing is published until every platform's package exists. release.sh keeps its shape (checks, builds, hashes.txt, upload, publish) and gains two platforms: the Mac part with the first Mac release, the Linux part with the first Linux release. release-please, the draft release and the tag stay as they are; linux/Cargo.toml gets its version from release-please, the Mac reads it from core/Cargo.toml at build time.

The order of a release

  • Checks first, failing fast: clean tree at the tag, CI green including the mac and linux jobs, the Windows machine reachable, Docker running, Xcode selected, every signing credential present, the GPG passphrase asked up front
  • Windows (slowest, another machine), then the Mac (notarization takes minutes), then Linux, each into dist/; --version is added to every shell in Phase 0 as the boot test
  • One hashes.txt, upload with --clobber, publish as latest
  • Then generate_appcast over the DMG and a push of appcast.xml to inboxclassic.com; later the Flathub manifest bump
  • PLATFORMS=windows,mac,linux rebuilds one platform after a failure; BUILD_ONLY=yes stays

Keeping three shells in step

Every feature becomes UI work three times. These rules make a missing third visible, and the ones marked as gates make it a failed build or a failed CI run rather than something to remember.

  1. The core computes, the shells show. Every string, count and decision a user sees comes from the core; a shell reads values and calls operations.
  2. One command table, three generated enums.build gate core/commands.toml holds every command with its label, shortcuts, icon and help anchor; each shell handles the generated enum exhaustively, so a new command fails the build of the shell that ignores it.
  3. One scenario, three drivers, one check.CI gate The end-to-end steps are written once; PowerShell, XCUITest and dogtail implement them and save screenshots under the same names. feature-map.mjs --check fails a platform whose screenshots miss a feature.
  4. One help, one icon set, one version, one changelog. help.html filtered per platform in Rust, the Fluent SVGs rendered for each toolkit by build-icons.sh, the version in core/Cargo.toml, release-please as it is.
  5. One release, one homepage. release.sh builds every platform's package, boot-tests each with --version, signs one hashes.txt, uploads everything, publishes the draft, then the Sparkle appcast. The homepage shows a download and the screenshots of each platform, refreshed from the three end-to-end runs.
  6. A PR touches all three or says why.CI gate When the C header, the command table or the feature list changed, app/, mac/ and linux/ must all have changed, unless the PR carries the label shells: partial and names what is left for which platform.
  7. A parity table by feature. docs/shells.md maps each feature to its file and function on each platform.
  8. CLAUDE.md knows all three. What each shell is, where each window lives on each platform, how to build, run, screenshot and test each, and the order of work for a feature: core and its tests, the command table or header, the three shells, the scenario step and feature-map entry, the help.

Decisions and risks

Decisions, confirmed 2026-11-04

  • Native look on the Mac and on Linux, the Outlook Express look stays Windows-only. Same layout, features, icons and words everywhere.
  • Apple silicon only, macOS 26 or newer now, 27 soon. Intel Macs on 26 are out; a universal binary is a day's work if that changes.
  • Ubuntu 26.04 LTS or newer, .deb first, Flatpak second, no snap.
  • Linux shell in Rust against pe-core; the Mac shell in Swift against the C ABI; app/ keeps its name.
  • Developer ID and Sparkle, not the Mac App Store, so no App Sandbox.
  • Every release built from the release Mac, all platforms, published together; no signing keys on GitHub.
  • The homepage detects the platform and shows all three, with each platform's own screenshots.
  • One developer, the Mac first, then Linux: about six months.

Risks

  • A WebKit load that cannot be refused. The spike comes first; the fallback is stripping the construct in pe-html for the WebKit document.
  • Keychain prompts on dev builds when the signing identity changes: sign Debug builds with the Developer ID, or run with --memory-passwords.
  • No tray on vanilla GNOME. Ubuntu ships the AppIndicator extension; elsewhere the app quits with its last window.
  • Headless AT-SPI flakiness. Waits and retries as in ui-e2e.ps1; the VM for what the container cannot show.
  • Three times the UI work per feature. Only the gates above keep it honest.
  • A release that fails halfway. PLATFORMS= rebuilds one platform and the upload takes what is in dist/, so a release never starts over.
