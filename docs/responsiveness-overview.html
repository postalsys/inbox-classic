Instant feedback, then the data

Clicking All Inboxes waits for the message list before the folder row even shows as chosen. The same pattern runs through the app: every list query runs on the window thread, inside the click. This review measures it, says what a principal mail app does instead, and proposes a plan in three steps for Windows, the Mac and Linux.

16 November 2026 · measured on a synthetic store of 3 accounts, 232,000 messages (Inboxes of 30k, 60k and 100k, a third in conversations), M5 Pro with the file cache warm: a cold disk or the Windows build machine is several times slower · no board post matches

What happens today

The click waits for the list

  • All three apps run the list work inside the tree's selection-changed handler, so the new highlight paints only after it.
  • For All Inboxes grouped by conversation (the default): counts, row count and the first page, about 80 ms here, several times that on a real disk or a slower PC.
  • Startup runs the same path plus finding the newest message (about 90 ms more) before the first paint.

Why the queries are slow

  • Grouping by conversation runs GROUP BY thread_id over every message of the list for each page, each click on a row, and Next Unread (55 to 130 ms).
  • Window functions over the whole list: a message window's previous and next (110 to 250 ms), finding a message's row (up to 130 ms), Select All (675 ms grouped).
  • Counts read every Inbox row, and twice when not grouped.
  • Sorting several folders by sender has no index: the last page takes 750 ms.

Where else the window freezes

  • Syncing: each change to the folder shown reloads the list at once (about 170 ms in All Inboxes), so it stutters while mail arrives.
  • Every click on a row in a grouped list: 55 to 85 ms.
  • Opening a message reads its whole source on the window thread; Reply, Forward, a draft and an attachment parse and decrypt there.
  • Mark All Read on 20,000 unread: about 2 s. Moving or deleting many: one long transaction on the window thread.
  • The Address Book searches on every key press.

A real bug

  • A search grouped by conversation, then Expand All: 6.7 seconds frozen. SQLite probes every open conversation for every search hit (a cross product). All three apps.
  • Background work (saving files, pictures) takes the same store lock, so the window also waits behind it.

The principle

Answer the hand at once; bring the data as soon as it is there

Within one frame (16 ms)

  • The row clicked is highlighted, the folder bar and window title say where you are, the keyboard focus moves
  • Nothing that reads the store runs in the click

Within 100 ms

  • The list shows the new folder: counts and the first rows
  • Until then the previous list stays, quietly dimmed, never an empty flash

After 400 ms

  • Only then a small "Loading" in the list (a slow disk, a huge search), never a spinner for short waits
  • A newer click wins: a list nobody waits for any more is thrown away
Click All Inboxes 0 ms row highlighted, title "All Inboxes", folder bar, focus (window thread) 0 ms request: list of All Inboxes, generation 7 (core, its own read connection) previous list dimmed, still scrollable 60 ms counts + first 100 rows of generation 7 arrive → list drawn, status bar counts (generation 6 arriving later is dropped) 400 ms only if nothing arrived yet: "Loading..." in the list

Step 1: paint first (quick wins)

Feedback before the queries

one PR, three apps

Folder click

  • The selection handler only records the row and schedules the list load for after the paint (Windows: PostMessage; Mac: perform after the run loop turn; Linux: idle callback). The highlight, title and folder bar paint at once
  • The old list is dimmed until the new one is drawn
  • Startup: show the window with the tree first, then the list

Core fixes

  • The grouped count with a search: materialize the conversations first, then count (6.7 s to milliseconds)
  • Not grouped: the row count is the count already made, not a second query
  • A list's sort no longer re-checks the folder's counts on every page (Linux paid two COUNTs per page)
  • A grouped row click uses the page already in memory, not a new GROUP BY

Quieter while syncing

  • Changes to the folder shown are gathered for 300 ms, as All lists are already
  • A reload during sync refreshes counts and the visible rows only, keeping scroll and selection without finding the row again
  • Address Book search waits 150 ms after the last key

Step 2: lists off the window thread

One request, one answer, newest wins

core + three apps

The core

  • pe_list_view_load(view, generation): counts, row count, the first page and the selected row's place, computed on a read connection of its own (WAL lets it read while sync writes), answered with a ListReady event
  • Later pages the same way, prefetched one page ahead
  • The pattern of message views today: the newest request wins, older ones are cancelled

The apps

  • Draw from the snapshot the event brings; never query in a paint
  • Rows not yet here show as blank lines of the right height (no jumping), filled when their page arrives
  • Sort, grouping, Hide Read and Expand All use the same load

Also off the window thread

  • Opening a message: its source read in the background, as parsing already is
  • Reply, Forward, drafts, attachments
  • Mark All Read, moving and deleting many: done in the background, the list updated at once (the rows disappear or turn read); if the server refuses, the rows come back and a bar over the list says why
  • Select All gives its count at once; the full list of messages only when a command needs it

Step 3: queries that do not grow with the mailbox

Big lists cost what small ones do

core, a migration

Counts kept, not counted

  • Each folder's total and unread kept in the folders table, updated as messages change
  • All Inboxes, All Sent and All Drafts add up their folders: instant at any size

Conversations summarized

  • A table of each conversation in each folder (newest date, count, unread, flagged), indexed by folder and date
  • The grouped first page reads it by index across the Inboxes instead of grouping every message

Paging by key

  • Pages, previous and next, and a message's place found from its sort key with an index, not by OFFSET or window functions over the whole list
  • Sorting several folders by sender or subject: indexes for those orders too

How it is checked

  1. The benchmark used for this review becomes a test of the core: a store of 230k messages built once, each list operation timed against a budget, run in CI.
  2. Each app's UI test measures the time from a folder click to the row highlighted and to the list drawn, with a large store, on all three platforms.
  3. A UX review of the waits from screenshots and screen recordings: no empty flashes, no jumping rows, the loading words only after 400 ms.
  4. /simplify and /security-review per pull request, as always.
