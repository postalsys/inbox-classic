The deep test: Inbox Classic on mailboxes the size people really have

An on-demand suite that runs all three apps against several accounts of thousands of messages each, does what a user does for a long time, and checks after every step that the window still shows what the server has.

Draft for review, 2026-11-20. Follows the 0.19.1 fix (#226). All decisions are made, with the folder selection added on 2026-11-20. The written plan is docs/deep-test-plan.md, the journeys are in scripts/ui-e2e/DEEP.md. Nothing is built yet.

What happened

On Linux, with a large Inbox, going to Flagged and back left a list of blank rows that opened nothing. It shipped in 0.19.0 with every test green.

The list of a 950 message folder, as pages of 100

The window keeps 8 pages. GTK read every row when the list was replaced, so all 10 pages were asked for at once and the first two were pushed out again. Those are the ones on screen.

Why no test saw it

  • The UI tests use folders of 4 to 30 messages. No list ever had a second page, let alone a ninth.
  • The speed test has 229,000 messages, but it calls the core. The core was right all along.
  • It needed a sequence (a list replaced while another was shown), not one action.
  • It needed one toolkit's habit. The Mac and Windows read only the rows in sight.

What that says about the gap

  • Nothing tests the windows at scale. Each app has its own cache of pages between the core and the screen (Windows keeps 8 pages of 100 too).
  • Nothing tests long sequences. The user's words were "eventually all folders are empty".
  • Nothing compares the screen with the server continuously. Each step checks only what it just did.

The suite

Five layers. The lower ones are cheap and find the core's bugs before a window is involved. The upper ones are where this incident lived.

1. The worldwhat the servers hold
A mailbox generator with a seed: accounts, folder trees, messages with real shapes (conversations, attachments, flags, dates over years, other scripts, a few huge ones). Built once into an ImapKit snapshot and loaded in seconds, so no run spends ten minutes adding mail. One ImapKit plays every account (it has users). The same seed gives the same world on every platform.
2. The checksafter every step
One set of things that must always hold, compared with the server over ImapKit's REST API:
  • the list has as many rows as the server has messages for that view;
  • no row in sight is blank once the app is quiet, and the rows in sight are the server's, in the sort order;
  • the selected row's message is the one in the reading pane;
  • every folder's total and unread count match the server; no message is listed twice;
  • nothing the window shows belongs to a folder left behind.
3. Journeyswritten, named
One for each family above: a fixed sequence with its own checks, as the regular scenario has, but in the big world. They are the readable part and the list a release is judged by. They go into scripts/ui-e2e/DEEP.md the way steps go into SCENARIO.md.
4. The walkrandom, with a seed
Thousands of steps drawn from a table of what a user and a server can do (click a folder, scroll, sort, search, select, delete, move, flag, reply, send, switch accounts; new mail, another client's changes, a dropped connection), with the checks after each. Some stretches run "fast fingers": several actions before anything has come back. A failure prints its seed and step, and the run can be played again up to that step. This is the layer that finds "eventually".
5. Healthover the run
Memory, open files, IMAP connections and the store's size sampled through the walk. Judged as growth between the first and last third of the run, not as fixed numbers, so a slow runner fails nothing.

How it is built

One conductor, three small drivers decided

The world, the journeys, the walk and the checks are written once, in Rust (pe-testkit and a new pe-deep binary). Each app's UI test learns a short vocabulary: about 30 actions ("click folder X", "scroll to row N", "press Delete") and one "say what the window shows". The conductor sends lines, the driver answers lines.

> folder work/Inbox > scroll 4200 > observe < rows 18044 first 4188 blank 0 selected - pane - > select 4201 < rows 18044 selected 4201 pane "Re: Q3 numbers"

The same walk without a window

The conductor can also drive the core directly. That run takes minutes, needs no desktop, and tells a core bug from a window bug at once: the same seed fails in both, or only with a window. It can run on GitHub on a schedule, as the OpenPGP suite does.

Nothing new in the shipped apps

The drivers live where the UI tests live now: Linux's e2e feature, the Mac's in-process test host, PowerShell outside the Windows exe. No port, no pipe and no test command in a release build. The security review checks exactly that.

Running it

By hand

scripts/deep-test.sh linux, mac, windows, core or all. --seed, --steps, --until to play a failure again.

On GitHub decided

A workflow started by hand runs the three apps on GitHub's machines and is what a release reads. The core walk also runs weekly with a new seed, not a gate. Never part of a pull request's checks.

Before a release decided

release.sh refuses to start without a passing deep run of the commit, as it does for translations not reviewed. ALLOW_NO_DEEP=1 releases anyway, with a warning.

What a run leaves

A page like the feature map: the journeys with pass or fail, the walk as a timeline with its seed, the health curves, and for a failure the last 30 steps, a screenshot, the window's answer, the server's answer and a copy of the store.

What a failure becomes

Every bug the deep test finds is fixed with a small, fixed step in the regular scenario, as 27a was for this one. The deep test finds, the regular test keeps.

Beside it: a folder opens with a message

Asked for with this plan. Today a folder switch clears the selection on all three apps, so Inbox, Flagged, Inbox ends with "no message is selected". That is how the core was written, not a fault of one app.

The rule decided

  • The message left there. Every row of the folder tree remembers the one message shown in it. Coming back selects it and scrolls to it.
  • Else the newest. Nothing remembered, or the message is gone: the newest by date, wherever the sort puts it. An empty folder selects nothing.
  • Through a restart. Kept in the store: the folder shown and each folder's message come back.
  • No setting.

What keeps it from doing harm

  • It opens as a click does, so a folder's newest unread message is marked read. That is the price of "else the newest". It is marked read only after a second on screen, as a click is.
  • It never raises a question by itself: no passphrase prompt, no sign-in.
  • Only the folder that is drawn opens a message. Folders passed through with fast clicks or arrow keys open nothing.
  • Several selected messages are not remembered. Search, Unread Only and sorting keep today's rule.
  • The app's own choice wins: a notification's message, a search hit, Undo's rows.

The core decides, the store remembers, the three apps follow, in one pull request with its step in the regular scenario and a sentence in the help. It does not wait for the deep test; journeys D2, D3, D6 and D14 check it at scale.

The order of work

Each step is a pull request. Each one ends with /simplify, /security-review, prettier, the tests, and CI watched to the end. Bugs found on the way get pull requests of their own.
