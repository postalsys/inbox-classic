Safe sending, rules and comfort

The plan for eight features from the review: ten pull requests, each on Windows, the Mac and Linux at once, each tested end to end, reviewed from screenshots until nothing is left to improve, and merged to master before the next begins.

14 November 2026 · from 0.17.1 · the full plan is sending-rules-comfort-plan.md beside this page

Decided

  • A rule is a search query plus actions, matched by the search code itself.
  • Three ways to make a rule: Tools > Message Rules, "Create Rule…" on the search bar, Create Rule from Message.
  • Rules run on new Inbox mail only; applying to mail already there is an opt-in.
  • Mail a rule moves is still announced, unless the rule says "Do not notify".
  • A rule refuses in: and dates; list: is added to search and rules.

Decided, continued

  • Undo Send waits 10 seconds; Options offers Off, 5, 10, 20, 30.
  • Closing a message keeps asking; "Don't Save" removes an automatic-only copy.
  • Text Size has no keys; Ctrl+wheel and pinch are off too.
  • Flagged only, no saved searches yet.
  • Dark messages on the Mac and Linux only.
  • Work starts when you say go, each PR in its own worktree.

The features

1. Drafts saved automatically

MPR 1

Today a message is kept only when the user saves it. No compose window has a timer.

How it behaves

  • A recovery copy in the local store 3 seconds after the last change; works offline.
  • The copy in Drafts on the server once typing stops for 10 seconds, at most every 30 seconds. The status bar's "Saved in Drafts 14:02" is the feedback.
  • Nothing is saved until something is changed.
  • Closing still asks. "Don't Save" removes a copy only the automatic saving made.
  • After a crash, the messages being written open again, marked as restored.

How it is built

  • The policy (when to save what) lives in pe-core compose, driven by a clock, so the three apps share it.
  • New store table compose_recovery; the server copy is the existing save_draft.
  • Apps: report changes, one timer, open what the core lists at start.

Tests

  • Policy with a fake clock; ImapKit: one draft, replaced, removed on "Don't Save".
  • UI: type and wait; kill the app, start it, the message is back.

2. Undo Send

MPR 2

The Outbox already has a "not before" time, used for agents' 30 seconds. The user's Send gets one too.

How it behaves

  • Send closes the window. The main window says "Sending in 10 seconds" with Undo.
  • It is the existing Undo: Edit > Undo Send, Ctrl+Z or Cmd+Z, until the message goes.
  • Undo opens the message again as it was, attachments included.
  • Quitting sends what is waiting; it is never dropped.
  • Options: Wait before sending: Off, 5, 10, 20, 30 seconds.

Where the Undo button is

  • Windows: the status bar, where "Sent" shows today.
  • Mac: a bar under the message list.
  • Linux: a toast with a button, as GNOME apps do.

Tests

  • The race: undo just before and just after sending gives a window or a sent message, never both or neither.
  • ImapKit: nothing reaches SMTP before the wait; undone, nothing ever does.

3. "Did you forget the attachment?"

SPR 3

How it behaves

  • Only with no file attached, and only in what the user wrote: the subject and the text above the signature and the quote.
  • Words of all five languages are checked whatever the language of the windows.
  • "You wrote “attached”, but no file is attached." Go Back (default) or Send Anyway. No setting.

How it is built

  • In the core, next to the address check that already runs on Send; the words come from the catalogs.

Tests

  • Per language; quoted text and signatures ignored; a word inside another word ignored.
  • UI: asks, Go Back keeps the window, Send Anyway sends.

4. Text Size

SPR 4

How it behaves

  • View > Text Size > Smallest, Smaller, Medium, Larger, Largest, as Outlook Express had it. The check mark shows where it is.
  • For the reading pane, message windows and the text being written (as shown, not as sent). Remembered.
  • No keys, no Ctrl+wheel, no pinch: it changes only when chosen.

How it is built

  • Five radio commands in commands.toml; the core keeps the choice and gives the factor (80 to 140 percent).
  • Each web view's own zoom; the accidental paths turned off.

Tests

  • UI: Larger, the factor the web view reports, kept over a restart, Medium again.

5. Flagged

MPR 5

How it behaves

  • A Flagged row under All Inboxes, always there, with the number of flagged messages.
  • Every flagged message of every account, with the Folder column of search results. Not Deleted Items or Junk; a Gmail message once.
  • A message unflagged stays listed until another folder is chosen.

How it is built

  • One more scope in the store's search, beside Folder, All Inboxes and Everywhere. A saved search can later be another row of the same kind.

Tests

  • Store: several accounts, Gmail duplicates, the count.
  • ImapKit: a flag set by another client shows up and goes. UI: the row, the list, the empty state.

6. Send from another address

MPR 6

How it behaves

  • Account Properties > Other addresses: Add, Edit, Remove; an address and a name each.
  • From lists them under their account.
  • A reply goes from the address the message was sent to. Reply All leaves all own addresses out.
  • A server that refuses the address gets a plain explanation; the help covers Gmail's "Send mail as".

How it is built

  • Store table of addresses per account; Outgoing.from, checked in the core against that list at send time.
  • Everything that asks "is this me?" uses the set.

Tests

  • Reply address choice; pe-smtp conformance for From and the envelope.
  • ImapKit: sent as the alias, replied as the alias, a refused sender explained.

7. Message Rules

LPR 7 corePR 8 windows

A rule is one sentence: for new mail in the Inbox that matches this search, do these things.

┌ New Rule ────────────────────────────────────────────────┐ │ Name: [ Newsletters from Acme ] │ │ For new mail in the Inbox of: [ All accounts ▾ ] │ │ that matches: [ from:news@acme.example ] │ │ 42 messages in the Inbox match. [Show] │ │ do this: │ │ ☑ Move to folder [ Newsletters ▾ ] │ │ ☑ Mark as read ☐ Flag [ Red ▾ ] │ │ ☐ Archive ☐ Move to Junk E-mail ☐ Delete │ │ ☐ Do not notify │ │ ☐ Also apply it to the messages already in the Inbox │ │ [ OK ] [ Cancel ] │ └──────────────────────────────────────────────────────────┘

Three ways in

  • Create Rule… on the search results bar, with the query filled in.
  • Message > Create Rule from Message, filled with from: the sender, or list: for a mailing list.
  • Tools > Message Rules: the list, with on and off, New, Edit, Delete, Move Up, Move Down.

How rules run

  • On mail arriving in an Inbox after the rule was made, while the app runs (it stays in the tray). Not on an account's first sync.
  • Top to bottom; a rule that moves the message away is its last.
  • Marked read, junked or deleted mail is not announced; moved mail is, and opens where it went.
  • The status bar says "2 messages sorted by your rules"; Message Properties names the rule.

How it is built

  • Matching is the search itself, limited to the UIDs that just arrived, so a rule and a search can never disagree.
  • A rule with words for the text makes the worker fetch the new messages' text first.
  • Actions go through the existing move, archive, junk, delete and flag operations (Gmail labels included).
  • A message is handled once, so rules can not loop.
  • Not allowed in a rule: in: and dates, refused in the editor with the reason. New for search too: list:.

Tests

  • ImapKit: mail arriving over IDLE is moved, flagged, marked read; body words; Gmail labels; 5,000 messages applied in batches; a deleted target folder skips the rule and says so.
  • 50 rules against a batch of new mail in under 20 ms on the 489,000 message store.
  • UI on all three: list, editor with live count, from search, from message, a delivered message sorted, a bad query refused.

8. Messages in dark mode

LPR 9 corePR 10 Mac and Linux

The reading pane, the editor and the cards are fixed to light today, so a dark desktop shows a white page in a dark window.

The messageIn a dark window
Plain text, cards, fold buttonDark, with styles of their own.
Brings its own dark stylesShown as it asks.
Sets no backgroundsDark; text colors too dark to read are lightened. This is what people write in Gmail, Outlook and Apple Mail.
Has its own designLeft light, as designed (newsletters, receipts). Apple Mail does the same.
Being writtenDark editor; nothing about colors is added to what is sent.
PrintedAlways light.

How it behaves

  • Follows the system on the Mac and Linux. Windows stays classic and light.
  • One switch in Options: "Show messages on a dark background when the system is dark", on.
  • No white flash while a message loads.

How it is built and tested

  • All of it in pe-html, in Rust, while sanitizing: no script, the CSP unchanged.
  • A corpus of real-shaped mail with the expected decision for each; contrast tests.
  • UI: the reading steps run once more in dark; a message written in dark is checked on the server to carry no colors.

How each pull request is done

  1. Branch from an up-to-date master, in a git worktree of its own, since another session works in this checkout.
  2. The core and its tests: unit and migration tests, and e2e_core against ImapKit for everything that talks IMAP or SMTP.
  3. Commands and the C API, with the generated header and command tables committed.
  4. The three apps: Windows, the Mac, Linux.
  5. Words and help: English, then German, Estonian, Spanish and French drafts marked for your review; the help topics in each.
  6. UI end-to-end tests: the step in the scenario and in each platform's test, the entry in the feature map; run on all three and feature-map.mjs --check for each.
  7. UX, UI and product review from the screenshots, until nothing is left: as a principal UX designer and a mail client product expert, in English and the pseudo-language, light and dark: layout, spacing, wording, order, keyboard, focus, empty and error states, and how Outlook Express, Thunderbird, Apple Mail and Gmail do it. Note what could be better, fix it, take the screenshots again, review again. Stop when a round finds nothing.
  8. /simplify over the changed code, with the maintainability check.
  9. /security-review of the branch; fix what it finds, and go on.
  10. Format, clippy, the whole test suite, prettier, check-shells.sh.
  11. Commit in the usual order (feat(core), each app, i18n, help, e2e, then fix(ux), refactor, fix), push, open the PR, watch CI; real failures fixed, flaky jobs rerun at most 3 times.
  12. Merge with a merge commit once CI is green and the last review round found nothing. The next PR starts from the new master.

Windows screens that need the build machine's desktop while it is away are logged in build/windows-ux-pending.md and checked when it is back; CI's own Windows screenshots cover the rest.

Security notes

RulesNo action sends anything or deletes for good. Queries become bound SQL values, as in search. Folder targets are ids, checked to exist. One handling per message. Agents have no way to make, change or run a rule. "Apply to the messages already there" asks with the count first.
From addressChecked in the core against the account's own list when sending; that list changes only in Account Properties, never through an agent or anything in a message.
Recovery copiesUnsent mail in the local store beside the cached mail, removed when the window closes. Attached files are read again on restore; a missing one is reported.
Undo SendThe reopened message passes the editor's sanitizer like any draft. Agents' own wait and approval are not shortened by the new setting.
Dark modeOnly color values the sanitizer already parsed are rewritten. No script, no new sources in the CSP, nothing fetched to decide.
Text SizeCloses zoom paths; opens none.
